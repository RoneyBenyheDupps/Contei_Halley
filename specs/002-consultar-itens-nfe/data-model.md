# Modelo de dados — consulta de itens de NF-e

O XML preservado continua sendo a fonte de verdade. A primeira extração completa de cada versão grava os itens declarados; consultas posteriores leem esse conjunto armazenado. Versões com falha não têm conjunto de sucesso e são tentadas novamente em cada consulta. Referências ao esquema existente: `migrations/001_triagem_nfe.sql` e `specs/001-triagem-nfe-entrada/data-model.md`.

## Entidades e relações

| Entidade | Campos relevantes | Relações e invariantes |
|---|---|---|
| **DocumentoEntrada** (existente) | `id`, `empresaId`, `accessKey`, `scope`, `captureState`, `canceled`, `firstXmlOccurrenceId`, `latestValidXmlOccurrenceId` | A consulta exige `empresaId=1` e `scope='IN'`. A chave identifica a nota. Os ponteiros são projeções mutáveis; a seleção padrão, inclusive na evidência de novas decisões, deriva da última ocorrência XML válida em `(observedAt,id)`. Replay de XML antigo não pode regredir `latestValidXmlOccurrenceId` nem sobrescrever o cabeçalho (número, emitente, destinatário, `vNF`, emissão) projetado da versão mais recente. |
| **OcorrenciaDocumental** (existente) | `id`, `documentoId`, `kind`, `observedAt`, `rawPayload`, `sha256`, `isValidXml`, `validationErrorCode` | Cada versão é uma ocorrência imutável de `kind='XML'`, vinculada à nota. Apenas `isValidXml=1` habilita consulta de itens. A versão escolhida determina todos os campos extraídos; versões de outra nota, inválidas ou fora do escopo não são expostas. |
| **ItensNfeExtraidos** (nova) | `xmlOccurrenceId` (PK/FK), `itemsJson` (lista completa), `extractedAt` | Uma linha de sucesso por ocorrência XML válida. A lista preserva todos os `det` na ordem original, com `nItem` único, campos decimais como texto e ausências omitidas. A gravação é atômica após extração integral; nenhuma linha é criada para lista parcial ou falha. A credencial de execução lê e insere, mas não altera nem apaga conjuntos concluídos. |
| **ItemDeclarado** (dentro de `itemsJson`) | `nItem`, posição na lista, `product`, `taxes` | Identidade lógica `(xmlOccurrenceId,nItem)`. Um resultado `AVAILABLE` devolve a lista armazenada para uma única versão, sem misturar itens de versões distintas. |
| **DisponibilidadeItens** (resultado, não persistido) | `status`, `accessKey`, `xmlVersion?`, `items?`, `errorCode?` | `items` só existe em `AVAILABLE`. Sem XML válido, usar `AWAITING_XML`, `CANCELED_XML_UNAVAILABLE` ou `TECHNICAL_FOLLOWUP` do estado documental. Versão válida que não pode ser extraída integralmente retorna `EXTRACTION_FAILED`, mantendo sua referência e download. |
| **FalhaIntegracao** (existente, extensão mínima) | `id`, `documentoId`, `kind`, `xmlOccurrenceId?` novo, `state`, `firstAt`, `lastAt`, `attempts`, `resolvedAt?`, `safeDetail?` | Para `kind='ITEM_EXTRACTION'`, `xmlOccurrenceId` é obrigatório e referencia `OcorrenciaDocumental` da mesma nota indicada por `documentoId`; a gravação confere esse vínculo. No máximo uma falha aberta por versão; histórico resolvido permanece. Outras falhas existentes podem manter o campo nulo. |

## Forma dos dados declarados

- `product` usa os nomes de campos XML selecionados: `cProd`, `xProd`, `NCM`, `CFOP`, `CEST`, `cEAN`, `cEANTrib`, `uCom`, `qCom`, `vUnCom`, `vProd`, `uTrib`, `qTrib`, `vUnTrib`, `vFrete`, `vSeg`, `vDesc`, `vOutro`. Campos ausentes não entram no objeto. Textos e decimais são strings; zero e zeros decimais escritos no XML permanecem distinguíveis de ausência. `SEM GTIN` é texto declarado, não valor nulo inferido.
- `taxes` contém somente os grupos principais presentes entre `ICMS`, `IPI`, `PIS` e `COFINS`. Cada grupo tem `variant` (o nome do subgrupo declarado, como `ICMS00`, `ICMSSN101`, `IPITrib`, `PISQtde`) e `fields` com os nomes XML selecionados para código de situação, base, alíquota ou valor. `CST` e `CSOSN` permanecem distintos. `qBCProd`/`vAliqProd` e `qUnid`/`vUnid` conservam seus nomes para não confundir base quantitativa e alíquota por unidade com base monetária e percentual. Variantes ou campos relevantes desconhecidos dentro dos quatro grupos causam falha de extração quando não forem explicitamente reconhecidos como fora do escopo; não são omitidos silenciosamente.
- A projeção não incorpora `PISST`, `COFINSST`, `ICMSUFDest` ou outros grupos irmãos. Sua presença não é falha e seus bytes continuam no XML original. Nenhum campo da projeção é usado para determinar conformidade fiscal.

## Validação e transições

1. Conferir que a versão solicitada está entre as ocorrências XML válidas da nota autorizada. Sem seleção, escolher a última por `(observedAt,id)`; não confiar exclusivamente no ponteiro mutável. A mesma ordem rege o detalhe existente da nota.
2. Se `ItensNfeExtraidos` já contém a versão, devolver seus itens sem reextrair. Se não contém, conferir SHA-256 do `rawPayload` contra a ocorrência e extrair. Inconsistência do armazenamento é falha de integridade operacional, não resposta de itens nem XML alegadamente íntegro. A investigação/restauração preserva as ocorrências históricas.
3. Rejeitar DOCTYPE e namespace alheio à NF-e. Aceitar `det` somente como filho direto de `infNFe`; exigir pelo menos um item, `nItem` inteiro positivo e único, dentro do limite do leiaute. Um item sem grupo `prod` ou com `prod`/`imposto` repetido, um campo mapeado repetido, um subgrupo tributário ambíguo ou conteúdo relevante desconhecido dentro dos quatro grupos principais deixam a versão inteira em `EXTRACTION_FAILED`. Um campo opcional ausente ou grupo irmão fora do escopo não causa falha.
4. Após sucesso, inserir atomicamente uma única linha com a lista completa em `ItensNfeExtraidos` e resolver eventual falha `OPEN` da versão. A PK impede duplicação por consultas concorrentes; quem perde a disputa lê a linha já confirmada. Apenas depois da confirmação a API responde `AVAILABLE`. Consultas seguintes usam a linha armazenada. Não há substituição automática de uma extração já bem-sucedida; correção futura dessa projeção exige reprocessamento explícito e rastreável a partir do XML original.
5. Após falha de extração, não gravar linha de sucesso e criar ou atualizar uma falha `OPEN` vinculada a `xmlOccurrenceId`, com categoria segura e tentativas. Cada nova consulta dessa versão tenta de novo. Repetição não cria segunda falha aberta; sucesso posterior a resolve (`RESOLVED`, `resolvedAt`) sem apagar o registro. `technicalIssueActive` da nota não muda. A consulta de itens nunca muda decisão, revisão de triagem, XML ou checkpoint.
6. Alterações de situação documental (inclusive cancelamento) não alteram itens armazenados de uma versão. Nova versão XML válida torna-se padrão, mas cada versão anterior continua acessível.

## Mudança de esquema planejada

`migrations/002_itens_nfe.sql` é aditiva: cria `contei.ItensNfeExtraidos` com `xmlOccurrenceId bigint` como PK/FK para `OcorrenciaDocumental.id`, `itemsJson nvarchar(max) NOT NULL` com JSON válido e `extractedAt datetimeoffset(3) NOT NULL`. A gravação valida na aplicação que a ocorrência pertence à nota, é XML válido e que a lista é completa e não vazia; o banco assegura uma linha por versão. A credencial de execução recebe `SELECT, INSERT` nessa tabela e negação de `UPDATE, DELETE`.

A mesma migração acrescenta `FalhaIntegracao.xmlOccurrenceId bigint NULL`, FK para `OcorrenciaDocumental.id`, restrição que exige o campo para `kind='ITEM_EXTRACTION'`, e índice único filtrado para `(xmlOccurrenceId)` quando `kind='ITEM_EXTRACTION' AND state='OPEN'`. A gravação confere que `FalhaIntegracao.documentoId` é a mesma nota da ocorrência. Antes de executar no ambiente alvo, inspecionar versão, colunas, índices, permissões e backup reais; testar aplicação, reaplicação, rollback de falha e restauração em banco isolado. Não alterar permissões de `UPDATE`/`DELETE` das ocorrências ou decisões históricas.
